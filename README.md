# Triploom

A React Native travel app that makes it easier to organize trips with a large number of participants.

---

## Workflow

This project uses an **agentic coding workflow** — everyone runs their own AI agent to implement features. The conventions in this document are the single most important thing to read. They exist so that code generated by different agents stays consistent and composable.

Read this README before starting your agent. Point your agent at it too.

---

## Tech stack

You should understand what each library does before running your agent, so you can guide it and review its output.

### Expo & React Native

We use **React Native** (via **Expo**) to build a cross-platform mobile app from a single TypeScript codebase. Expo is a layer on top of React Native that provides a managed build system, a dev server, and a set of pre-built native modules (camera, haptics, etc.) so we don't have to write native code ourselves.

### Expo Router

Navigation is handled by **expo-router**, which is a file-based router built on top of React Navigation. Instead of registering screens in code, the folder structure inside `app/` *is* the navigation structure — similar to how Next.js works for the web. See the [Navigation](#navigation-expo-router) section for details.

### Supabase

**Supabase** is our backend. It provides:
- **Database** — a hosted Postgres database
- **Auth** — user sign-up, login, session management
- **Realtime** — live updates pushed to the app over websockets (used in chat)

We interact with Supabase through the `@supabase/supabase-js` client, which lives in `lib/supabase.ts`. All calls to this client go through `services/` — never directly from components or screens.

### Zustand

**Zustand** shares data between screens without passing props through every component.

**Without Zustand (the problem):**
```tsx
// Trip data needed on HomeScreen
function HomeScreen({ trip }) {
  return <Text>{trip.name}</Text>;
}

// Also needed on EventsScreen
function EventsScreen({ trip }) {
  return <Text>{trip.name} Events</Text>;
}

// Must pass through TripStack even though it doesn't use it
function TripStack({ trip }) {
  return (
    <Stack>
      <HomeScreen trip={trip} />     // pass down
      <EventsScreen trip={trip} />   // pass down
    </Stack>
  );
}
```

**With Zustand (the solution):**
```tsx
// Any screen can access trip directly
function HomeScreen() {
  const trip = useTripStore((state) => state.currentTrip);
  return <Text>{trip.name}</Text>;
}

function EventsScreen() {
  const trip = useTripStore((state) => state.currentTrip);
  return <Text>{trip.name} Events</Text>;
}

// No need to pass props through TripStack
function TripStack() {
  return (
    <Stack>
      <HomeScreen />     // no props needed
      <EventsScreen />   // no props needed
    </Stack>
  );
}
```

**Reading state:**
```ts
const trip = useTripStore((state) => state.currentTrip);
const messages = useChatStore((state) => state.messages);
```

**Calling actions:**
```ts
const { fetchTrips } = useTripStore();
await fetchTrips(); // Calls service and updates state
```

**Complete example — Store action calling service:**
```ts
// store/trip.store.ts
import { getTrips } from '@/services/trip.service';

export const useTripStore = create<TripState>()((set) => ({
  trips: [],
  isLoading: false,
  
  // Action calls service and updates state
  fetchTrips: async () => {
    set({ isLoading: true });
    const trips = await getTrips();  // calls service
    set({ trips, isLoading: false });
  },
}));

// Component using the store
function TripList() {
  const { trips, isLoading, fetchTrips } = useTripStore();
  
  useEffect(() => {
    fetchTrips();  // calls store → calls service → updates all subscribers
  }, []);
  
  if (isLoading) return <Text>Loading...</Text>;
  return trips.map(t => <TripCard key={t.id} trip={t} />);
}
```

**Note:** Currently stores have placeholder functions since we don't want to enforce implementation yet. When you build features, implement actions like the example above.

**Using outside components:**
In regular functions (not React components), you can access the store directly without the hook:
```ts
// In a service or utility function
import { useTripStore } from '@/store/trip.store';

const tripState = useTripStore.getState()
// Get current state
const currentTrip = tripState.currentTrip;

// Call action
tripState.setCurrentTrip(newTrip);
```

**Stores live in `store/` folder** — one file per domain (auth, trips, chat, etc.)

### Zod

**Zod** checks data at runtime. TypeScript checks your code, Zod checks actual data.

**Why:**
- User types in form → might type garbage
- API returns data → might be missing fields
- You can't trust external input

**Example — Form validation:**
```ts
const TripSchema = z.object({
  name: z.string().min(1, "Trip name is required"),
  destination: z.string(),
  start_date: z.string().datetime(),
});

// Validate what user typed
const result = TripSchema.safeParse(formData);
if (!result.success) {
  // Show specific error
  alert(result.error.errors[0].message);
  return;
}

// Now safe to use
createTrip(result.data);
```

**Example — API response validation:**
```ts
// API might return wrong shape
const response = await fetch('/api/trips');
const data = await response.json();

// Validate before using
const trips = TripArraySchema.parse(data);
// If data is wrong, Zod throws immediately
```

**Get TypeScript type from schema:**
```ts
type Trip = z.infer<typeof TripSchema>;
// Same as: { name: string, destination: string, start_date: string }
```

## Setup

### Prerequisites

- Node.js + npm
- Expo CLI: `npm install -g expo`
- Supabase CLI: `npm install -g supabase`

### Steps

1. Clone the repo and install dependencies:
   ```bash
   npm install
   ```

2. Get the Supabase credentials from the **#login-info** channel on Discord.

3. Go to [supabase.com](https://supabase.com), log in as the `triploom` user, and click **Connect** at the top. Select **Expo React Native** as the framework — that page shows exactly what goes in your `.env` file. Create the `.env` file in the project root.

4. Log in to the Supabase CLI so your agent can run Supabase commands:
   ```bash
   supabase login
   ```

5. Start the app:
   ```bash
   npm start
   ```

### Regenerating database types

`types/database.types.ts` is a TypeScript mirror of the Supabase schema. It gives the Supabase client full type safety — without it, queries return `any`.

```ts
// Without the Database type:
supabase.from('trips')  // → returns any[]

// With the Database type:
supabase.from('trips')  // → returns Trip[], with autocomplete on every column
export const supabase = createClient<Database>(url, key);
```

Regenerate it whenever the schema changes:

```bash
# Against the hosted project:
npx supabase gen types typescript --project-id <your-project-id> > types/database.types.ts

# Or against a local Supabase instance (after `supabase start`):
npx supabase gen types typescript --local > types/database.types.ts
```

Commit the regenerated file. Stores and services pick up the correct types automatically — no other changes needed.

## Git Workflow

**Commit regularly when using AI agents.**

AI can do something good, then suddenly break everything. Commit often so you don't lose progress:

```bash
# Good: Commit before running agent
git add .
git commit -m "before: adding event creation form"
# Run your agent...
# If it breaks something: git checkout . or git reset --hard HEAD

# Also good: Commit after agent finishes successfully
git add .
git commit -m "feat: add event creation form with validation"
```

**Rules:**
- Commit BEFORE running an agent on new work (savepoint)
- Commit AFTER agent finishes successfully (keep the good)
- Push to GitHub regularly so teammates see progress
- Write clear messages: `feat: add trip creation` not `update`

You can clean up/squash commits later. Don't lose work now.

      chat/

**Note:** `IS_AUTHENTICATED` and `HAS_SELECTED_TRIP` in layout files are temporary placeholders for early development. They let you access any screen before real auth/trip selection is built.

### `services/`

Services are the only place that talks to Supabase. Each file corresponds to one domain:

```
services/
  auth.service.ts       # sign in, sign up, sign out
  trip.service.ts       # fetch trips, create trip, update trip
  chat.service.ts       # fetch messages, send message
  events.service.ts
  tasks.service.ts
  profile.service.ts
```

**Why:**
- All API calls in one place — easy to find and update
- Consistent error handling everywhere
- Components stay simple (no API logic)
- Easy to mock for testing

A service function fetches or mutates data and returns the result. It does not hold state and does not know about the UI.

```ts
// services/trip.service.ts
export async function fetchTrips(userId: string): Promise<Trip[]> {
  const { data, error } = await supabase
    .from('trips')
    .select('*')
    .eq('user_id', userId);

  if (error) throw error;
  return data;
}
```

### `store/`

Stores hold global state and expose actions that components can call. Actions call services to do the actual data work.

```
store/
  auth.store.ts         # session, user, isLoading
  trip.store.ts         # activeTrip, trips list
  chat.store.ts         # messages
  events.store.ts
  tasks.store.ts
  home.store.ts
  profile.store.ts
```

```ts
// store/trip.store.ts
const useTripStore = create<TripState>((set) => ({
  trips: [],
  activeTrip: null,

  fetchTrips: async (userId) => {
    const trips = await fetchTrips(userId); // calls the service
    set({ trips });
  },
}));
```

The flow is always: **component → store action → service → Supabase**.

## Conventions

These rules keep AI-generated code consistent across agents. Follow them strictly.

### UI design system

Before changing UI, screens, reusable components, layout, colors, spacing, cards, images, or navigation chrome, read `constants/README.md`.

That file is the source of truth for design-token usage, the 60-30-10 visual balance, large image/content surfaces, and how Triploom should compose polished screens without becoming visually cluttered.

### Navigation (Expo Router)

Expo Router uses **file-based routing**. The folder structure IS the navigation.

### Route Groups

Folders in `(parentheses)` are route groups. They don't appear in the URL but control layout:

| Group | When shown |
|-------|------------|
| `(auth)/` | Login, signup, forgot-password screens |
| `(app)/` | All screens after logging in |
| `(app)/(no-trip)/` | Trip picker (no active trip) |
| `(app)/(trip)/` | Tab bar (has active trip selected) |

### Development Mode — Toggle Constants

While building features, change these constants to access different screens:

```tsx
// app/_layout.tsx — controls auth vs app
const IS_AUTHENTICATED = true;  // true = show (app), false = show login

// app/(app)/_layout.tsx — controls trip vs no-trip  
const HAS_SELECTED_TRIP = true; // true = show tabs, false = show trip picker
```

Change the value → Save file → App automatically reloads to the new route.

**These are temporary placeholders** for early development sessions. When real auth and trip selection are built, these will be replaced with actual state from stores.

### Navigation Rules

- **File structure = Routes**: `app/(app)/(trip)/events/index.tsx` → route `/(app)/(trip)/events`
- **Every screen**: Lives in its own folder as `index.tsx`
- **_layout.tsx**: Wraps all screens in that folder (adds stack, tabs, etc.)
- **Navigate with**: `router.push('/(app)/(trip)/events')` or `<Link href="...">`
- **Never**: Use `createStackNavigator` manually

### Components

Place components based on where they are used:

| Used in                  | Goes in                         |
|--------------------------|---------------------------------|
| Only one screen          | `components/<screen-name>/`     |
| More than one screen     | `components/ui/`                |
| Auth screens only        | `components/auth/`              |
| Trip screens only        | `components/trip/`              |
| Navigation/chrome        | `components/layout/`            |

If `components/ui/` grows large, split it further — but do not dump everything there by default.

### State management

- Global state lives in `store/`. One store per domain.
- Do **not** use React Context for state shared across screens. Use a Zustand store.
- Keep stores thin — they hold state and call services. Business logic belongs in `services/`.

### Data flow

```
Screen / Component
      ↓  calls action
   Zustand Store
      ↓  calls function
     Service
      ↓  queries
    Supabase
```

Never skip a layer. Components do not call services directly. Services do not hold state.

### Types

- Use `types/database.types.ts` for all database-related types.
- Use `zod` to define and validate types that cross system boundaries (form input, API responses).
